    CI/CD Pipeline¶

    This document details the Continuous Integration and Continuous Deployment workflows for the ichrisbirch project.

    Overview¶

    The project uses GitHub Actions for CI/CD with the following workflows:

    Workflow File Trigger Purpose
    CI validate.yml Pull requests, and called by a release Validate every component
    Release release.yml Push to main Call CI, then build and push the app images and tag and release the icb binary
    Deploy MkDocs deploy-docs.yml Push to main (docs changes) Build and deploy documentation
    Sync Documentation Code sync-docs-code.yml Push to main Sync code snippets in documentation

    CI Workflow¶

    validate.yml is generated by forge from the components the repo declares, so its per-stack jobs are not hand-edited. Repo-specific steps live in # > custom: blocks, which regeneration preserves.

    It carries no push: trigger on purpose. The release workflow calls it with uses:, so a push to main is validated inside the release run — against the commit being released rather than whatever finished CI last.

    Jobs¶

    generated from declared components
├── python      ruff check, ruff format, mypy, pytest
│                 (custom: SOPS secrets, first)
├── go-cli      build, vet, test, golangci-lint, govulncheck
├── vue-frontend  eslint, npm run build (vue-tsc + vite)
├── terraform   fmt, init, validate, test
└── shell       shellcheck, shfmt, bats

custom, because no generated block covers them
├── vue-unit          vitest run
├── e2e               Playwright inside the test stack's vue container
└── production-build  build the production images and start them

    The last three are jobs rather than steps on an existing job. A custom:after:<component> block is read as far as the next # generated: marker, which sits below the following job's header — so on any component but the last, such a block swallows that header and forge emits it twice.

    pytest starts its own services, in CI as on a workstation¶

    The python job decrypts secrets/secrets.test.enc.env to .env and runs the generated uv run --with pytest pytest. Each session starts its own Postgres and Redis on the runner's Docker through testcontainers, so no compose stack runs for that job. Test Environment covers how.

    The e2e job runs the workstation's commands¶

    ./ops/icbops testing start
./ops/icbops test e2e

    The job first writes .env and a self-signed certificate for *.test.localhost, because Traefik will not start without one. GitHub sets CI=true, and icbops then adds docker-compose.ci.yml to the compose set. That file removes the API's Docker socket mount. test e2e passes CI into the vue container, where the Playwright config retries a failed test and refuses .only.

    The project is icb-test-ichrisbirch, after the checkout's directory. Each job runs on its own hosted VM, so no two jobs share a Docker daemon. The job saves the stack's logs to frontend/test-results/stack.log and uploads that directory with the JSON report, on a pass as well as a failure.

    Deploy MkDocs Workflow¶

    Builds and deploys documentation to GitHub Pages.

    Trigger Conditions¶

    on:
  push:
    branches: [main]
    paths:
      - 'docs/**'
      - 'mkdocs.yml'
      - 'mkdocs_plugins/**'

    Custom MkDocs Plugins¶

    The project uses custom MkDocs plugins that must be installed:

    • code_sync - Synchronizes code snippets in documentation
    • diagrams - Generates architecture diagrams

    These are registered as entry points in pyproject.toml:

    [project.entry-points."mkdocs.plugins"]
code_sync = "mkdocs_plugins.code_sync.plugin:CodeSyncPlugin"
diagrams = "mkdocs_plugins.diagrams:DiagramGeneratorPlugin"

    The workflow uses uv sync to install all dependencies including these plugins.

    Troubleshooting CI Failures¶

    Common Issues¶

    1. The e2e job's stack does not start¶

    ./ops/icbops testing start failing names the unhealthy service. The playwright-evidence artifact holds stack.log, every container's output.

    2. pytest cannot start its services¶

    Could not start the Postgres and Redis this session runs against

    Docker on the runner refused a container. The step's log carries Docker's own error just above it.

    3. MkDocs plugin not found¶

    Error: The "code_sync" plugin is not installed

    Ensure workflow uses uv sync instead of just pip install mkdocs-material.

    Viewing CI Logs¶

    Use the tracking script to view workflow logs:

    # List recent runs
./scripts/track-gh-actions-workflow.sh list

# Watch a running workflow
./scripts/track-gh-actions-workflow.sh watch

# Get failure logs
./scripts/track-gh-actions-workflow.sh logs

    Or use the GitHub CLI directly:

    # List runs
gh run list

# View specific run
gh run view <run-id>

# Get failed job logs
gh run view <run-id> --log-failed

    Local Testing Before Push¶

    To catch CI issues before pushing:

    # Run linting
uv run ruff check .
uv run ruff format --check .

# Run type checking
uv run mypy ichrisbirch/

# Run both suites the way CI does
./ops/icbops test run
./ops/icbops test e2e

    Workflow Files Reference¶

    File Purpose
    .github/workflows/validate.yml Main CI workflow, generated by forge
    .github/workflows/release.yml App image build and push, and the icb binary release, gated on CI
    .github/workflows/deploy-docs.yml Documentation deployment
    .github/workflows/sync-docs-code.yml Code sync in docs
    docker-compose.ci.yml CI-specific Docker Compose overrides, added by icbops under CI=true
    tests/environment.py PrivateServices, pytest's own Postgres and Redis
